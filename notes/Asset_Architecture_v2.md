# 🏛️ KeiAI Asset System Architecture 2.0 (Local-First & E2EE)

이 문서는 KeiAI 플랫폼의 핵심인 '에셋 파이프라인'에 대한 최종 명세서입니다. 단대단 암호화(E2EE), 클라이언트 주도(Local-First), 그리고 서버 스토리지 및 트래픽 비용을 극한으로 방어하는 1인 소유권(Single Owner) 및 원격 저장소 무임승차(Freeriding) 아키텍처를 정의합니다.

---

## 1. 에셋의 종류 (Kinds)

어떤 데이터 환경(컨텍스트)에서 생성되었느냐에 따라 3가지로 나뉩니다.

1. **인레이 (Inlay)**
   - 세션(채팅) 도중 단발적으로 생성되는 이미지들 (유저가 업로드하거나 AI가 생성한 이미지).
   - 채팅 내부에 `{{inlay::<uuid>}}` 와 같은 형식으로 텍스트에 삽입되어 참조됩니다.
   - 프라이빗 에셋과 기술적으로 동일하지만, 유저가 명시적으로 켜지 않는 한 **기본 동기화 OFF (로컬 전용)** 상태를 가집니다.

2. **프라이빗 (Private)**
   - 유저가 개인적으로 올린 캐릭터 아바타, 배경 이미지, 표정 등 핵심 자원.
   - 무조건 개인 소유이므로 서버 업로드 시 프라이빗 쿼타를 소비하며, E2EE 암호화 처리됩니다.

3. **퍼블릭 (Public)**
   - Hub(오픈 커뮤니티)에 공개된 캐릭터/모듈 등에 묶인 에셋.
   - CDN을 통해 평문으로 제공되며 누구나 접근 가능합니다. (프라이빗 쿼타 소모 없음)

---

## 2. 에셋의 2가지 상태 (States)

- **로컬 (Local)**: 아직 서버에 업로드되지 않은 상태. (업로드 큐 대기 중이거나, 인레이 동기화가 꺼져있는 경우)
- **리모트 (Remote)**: 서버(클라우드)에 무사히 동기화가 완료된 상태. 기기 용량 관리를 위해 지워져도(LRU 캐시 방출) 나중에 다시 다운받을 수 있는 안전지대입니다.

---

## 3. 에셋 생성 및 전처리 (Client-Side Compression)

모든 에셋(이미지)은 파일 시스템이나 서버 핏줄을 타기 전에 **가장 앞단에서 압축**됩니다.

- 30MB의 무손실 이미지를 올려도 서버나 로컬에는 그 용량대로 가지 않습니다.
- 이미 규격에 맞는 이미지는 해시값을 유지할 수 있도록 건들이지 않습니다.
- 브라우저(클라이언트) 단에서 기본 WebP 변환 및 리사이징(예: 1080p, 최대 5MB 이하)을 강제합니다.
- 서버는 이 크기 검증만 하며, 초과 시 즉시 `413 Payload Too Large` 에러로 튕겨내 트래픽 터짐과 브라우저 메모리 폭발(OOM)을 막습니다.

---

## 4. 데이터베이스 및 스토리지 구조

### 4.1. 유저 에셋 테이블 (`assets` / EncryptedRecord)

이 유저가 보유한 모든 에셋 데이터의 **진실의 원천(Source of Truth)**입니다. Blind Sync 엔진을 통해 동기화됩니다.

- **id**: 에셋의 고유 ID (UUID). 동일한 에셋 원본이더라도 임포트 시마다 무조건 다르게 생성되어 각각 고유의 생명주기를 가집니다.
  - 이로 인해 같은 에셋이 로컬 저장소에 중복되어 저장될 수 있지만, 드문 케이스이고 GC가 어려운 E2EE의 특성 상 수용 가능한 트레이드오프 입니다.
  - 에셋 서버 (CDN)에 업로드 할 때는 SHA256 해시값을 id로 쓰므로 중복 업로드를 방지합니다.
- **userId**: 해당 에셋을 업로드/임포트한 유저.
- **createdAt**, **updatedAt**, **isDeleted**
- **encryptedData**: 아래 `AssetFields` 데이터를 E2EE로 감싼 암호문.
- **encryptedDataIV**: 복호화 초기화 벡터.

> **AssetFields (복호화 시 나오는 알맹이)**
>
> - `kind`: inlay | private | public
> - `encKey`: `SHA256(plaintext + FIXED_SALT)`. 프라이빗 에셋을 R2에 올릴 때 이 키로 파일을 지퍼백처럼 잠급니다.
> - `hash`: `SHA256(plaintext)` 파일 평문의 해시값. 클라우드에 올릴 때 이 텍스트가 물리적인 '파일명'이자 '접근 URL 경로'가 됩니다.

### 4.2. 에셋 메타 테이블 (`assetRegistry` / Local Plaintext Table)

로컬 에셋 스토리지 FS에 담긴 모든 에셋의 로컬 상태(동기화 큐, LRU 캐시 관리)를 관장하는 얇은 평문 테이블입니다. 현재 기기(Device)의 상태만 관리하므로 **다른 기기와 동기화되지 않습니다.**

- `id`: 에셋의 고유 ID (`AssetFields.id`와 동일).
- `kind`: `private` | `inlay` | `public` (워커가 복호화 없이 필터링하기 위한 평문 프록시).
- `status`: local | remote | deleting
- `size`: 로컬 파일의 크기. (캐시 총량 제한 계산용)

### 4.3. LRU 캐시 관리

로컬 스토리지 용량을 관리하기 위한 Watermark 기반 LRU 방출 정책입니다.

- **High Watermark**: 500MB. 캐시 총량이 이 값을 넘으면 방출 시작.
- **Low Watermark**: 400MB. 방출은 이 값 아래로 떨어질 때까지 수행.
- **대상**: `status === 'remote'`인 에셋만 방출. `local` 상태는 원본이므로 제외.
- **방출 순서**: `updatedAt` 오름차순 (오랫동안 안 쓴 것부터).

### 4.4. 로컬 스토리지 (OPFS / Tauri FS)

평문으로 압축(WebP)된 에셋 바이너리 파일들이 저장되는 실제 폴더입니다.

- 모든 파일은 `/assets/<id>` (UUID) 이름으로 저장됩니다.
- **두 가지 역할을 동시에 수행**:
  1. 서버에 아직 올라가지 않은 로컬 상태 에셋들의 **영속 저장소 (원본 보관상자)**.
  2. 서버에 올라간 리모트 상태 에셋들의 **LRU 캐시 저장소**.

### 4.4 에셋의 라이프사이클

1. local inlay -> remote inlay
2. local private -> remote private
3. local private -> remote public
4. remote private -> remote public

## 5. 백그라운드 Sync 엔진

UI 렌더링을 방해하지 않고 백그라운드에서 조용히 도는 '로컬-퍼스트의 심장'입니다.

- **인메모리 글로벌 상태**: `idle` | `syncing` | `network_error` | `quota_error` 등 글로벌 동기화 상태를 가져, 문제 발생 시 불필요한 재시도로 배터리/대역폭을 낭비하지 않습니다.
- **동작 방식**:
  1. 에셋 메타 테이블에서 `status`가 `local`이고 `kind`가 `private` (유저가 설정을 켰다면 `inlay`도) 인 리스트를 뽑습니다.
  2. 순차적(또는 가벼운 병렬)으로 처리합니다.
  3. 해당하는 녀석들은 `hash` 이름으로 서버에 업로드를 시도합니다 (`POST` API).
  4. 모종의 이유(402 Quota Exceeded 등)로 실패 시, 성공한 것까지만 처리하고 해당 세션 동안 동기화를 일시정지(`failed`)시킵니다.
  5. 정지 상태에서 특정 이벤트 (인터넷 재연결, 유저가 다른 봇을 지워서 용량 확보 등) 발생 시 다시 큐를 재가동합니다.

## 6. 리모트 저장소 (Cloudflare R2 CDN)

원격지는 서버 유지비 방어를 위해 프라이빗과 퍼블릭을 논리적으로 분리하지 않고 **하나의 거대한 통합 저장소**를 씁니다.

모든 에셋은 CDN에서 평문의 `해시값(Storage_Hash)` URL로 직접 제공됩니다. (서버 I/O 트래픽 부하 제로)

- **프라이빗 에셋**: `https://cdn.../<hash>` 로 누구나 다운받을 수 있지만, 파일 내부가 `암호화 키`로 잠겨 있어 쓰레기 바이트로 보입니다. (E2EE)
- **퍼블릭 에셋**: 똑같이 `https://cdn.../<hash>` 접근이며, 암호화되지 않은 투명한 파일입니다.

## 7. 서버 에셋 관리 테이블 (PocketBase)

에셋의 **소유권, 종류(Kind), 과금(Quota), 그리고 삭제 통제**를 판별하는 서버 장부입니다.

- **해시 (`hash`)**: 평문의 해시값 (에셋 고유 PK).
- **userId (`ownerId`)**: 이 에셋을 **맨 처음** 서버에 올린 유일한 1명의 유저. (소유권자)
- **종류 (`kind`)**: `private` | `public`. 프로모션 후 `public`으로 변경되어 쿼타 관리에서 제외됩니다.
- **레퍼런스 카운트 (`refCount`)**: '현재 이 주인(Owner)이, 본인 로컬의 몇 개의 봇에서 이 에셋을 중복으로 쓰고 있는가'를 나타내는 참조 횟수.
- **크기 (`size`)**: 에셋의 크기. (이 주인의 프라이빗 쿼타에서 깎여있는 용량)

> **무임승차 (Deduplication Freeriding) 원리**
> B유저가 A유저(주인)가 올린 똑같은 해시 에셋의 업로드를 시도하면, 서버는 200 OK(스킵)를 반환하고 파일을 다시 받지 않습니다. B유저는 자신의 쿼타가 깎이지 않으며, 서버의 장부(레퍼런스 카운트 등)에도 B의 정보는 남지 않습니다. 오직 A의 쿼타와 파일만 남습니다.

### 7.1. 유저 테이블 쿼타 관리 (PocketBase users)

프라이빗 에셋의 쿼타 제한을 관리합니다. 에셋 업로드/삭제 시 차감/환급됩니다.

- `assetQuota` (number): 유저의 프라이빗 에셋 총량 제한 (bytes).
- `assetUsage` (number): 현재 사용 중인 용량 (bytes).

## 8. Asset Sync Service (Client-Side)

백그라운드에서 동기화 큐를 처리하는 클라이언트 서비스입니다. Comlink 기반 Worker 패턴을 사용합니다.

### 8.1. Worker 인터페이스

```typescript
// lib/workers/asset-worker.ts
interface AssetWorker {
  // 이미지 압축 및 해시 계산
  compressAndHash(
    file: File,
  ): Promise<{ blob: Blob; hash: string; encKey: string }>;

  // AES-GCM 암호화
  encrypt(data: ArrayBuffer, key: Uint8Array): Promise<Uint8Array>;
}

// lib/adapters/asset/web.ts
class WebAssetAdapter {
  private static worker: Remote<AssetWorker> | null = null;

  static getWorker(): Remote<AssetWorker> {
    if (this.worker) return this.worker;
    const worker = new Worker(new URL("./asset-worker.ts", import.meta.url), {
      type: "module",
    });
    this.worker = wrap<AssetWorker>(worker);
    return this.worker;
  }
}
```

### 8.2. Sync 서비스 인터페이스

```typescript
class AssetSyncService {
  // 큐 관리
  static enqueue(assetId: string): void;

  // 라이프사이클
  static start(): void;
  static stop(): void;

  // 상태 조회
  static getState(): AssetSyncState;

  // 프라이빗 -> 퍼블릭 프로모션
  // 내부에서 현재 작업 완료 대기 + 큐에서 제거 처리
  static async promote(assetId: string): Promise<void>;
}

interface AssetSyncState {
  status: "idle" | "syncing" | "network_error" | "quota_error";
  pendingCount: number;
  currentAssetId?: string;
}
```

## 8. 런타임 파일 접근 및 파이프라인 (Read & Decode)

클라이언트가 화면에 에셋을 띄우려 할 때 온디맨드(Lazy Load)로 가져오는 흐름입니다.

1. **로컬 FS 확인**: 먼저 `/assets/<id>` 가 폰에 있는지 확인합니다. 있으면 즉시 로드 (메타 테이블의 `updatedAt`은 DB 어댑터가 자동 갱신).
2. **원격 다운로드 다운로드**: 캐시 미스(로컬에 없음)이고 상태가 `remote`라면, `AssetFields`에 있는 `해시값`을 조합해 CDN URL로 다운로드합니다.
3. **복호화 파이프라인 (The Magic Validator)**
   - 만약 CDN URL 캐싱 실패(404 에러)라면? 서버에서 영구 삭제된 엑박 데이터입니다. (주인이 파일을 날렸음)
   - 정상적으로 바이너리를 받아왔다면, 브라우저가 **이미지로 인식(Valid)하는지** 체크합니다.
     - **Valid (퍼블릭)**: 이미지 원본 평문 구조가 맞으므로, 그대로 로컬 FS 캐시에 저장하고 반환합니다.
     - **Invalid (프라이빗)**: 암호화되어 깨진 파일이므로, `AssetFields`의 `암호화 키`를 사용하여 AES-GCM 복호화를 시도합니다.
     - 복호화 후 결과가 Valid하면, 맑아진 원본 이미지를 로컬 FS 캐시에 저장하고 반환합니다.
     - 복호화마저 Invalid하다면 잘못된(망가진) 에셋입니다.

## 9. 익스포트 및 오프라인 생존 (Two-Track Export)

에셋 서버는 데이터(파일)와 암호화 키를 분리합니다. 다운로드 주소는 오픈되어 있지만 프라이빗 파일을 푸는 '열쇠'는 봇이나 모듈을 내보내기/공유할 때 그 JSON 내부에만 적혀 나갑니다.

- **가볍게 내보내기 (링크 공유)**: 오직 메인 프로필 사진(아바타) 1장만 PNG로 구워 호환성을 맞추고, 내부의 나머지 수십 장 프라이빗 에셋들은 `hash`와 `encKey` 텍스트로만 남깁니다. 파일은 매우 가벼워지며, 받은 사람은 앞선 '무임승차 파이프라인'을 통해 쾌적하게 셋업합니다. (단, 주인이 원본을 날리면 나중에 엑박이 될 위험 내포)
- **독립형 내보내기 (바이너리 굽기)**: 게스트 유저(오프라인)의 유일한 공유 수단. 모든 에셋을 전통적인 Base64로 통째로 구워버립니다. 파일은 무겁지만 오프라인에서 무조건 생존합니다. 누군가 이 카드를 다시 임포트하면, 시스템은 그 텍스트 덩어리를 다시 바이너리로 쪼개어 `/assets/<id>` 로컬 체계로 완벽히 원상 복구(소화) 시켜버립니다.

## 10. 서버 측 API 명세 (PocketBase)

서버는 무거운 비즈니스 로직 없이, E2EE 원칙에 따라 철저하게 **소유권 검증**과 **안전한 GC(삭제)** 역할만 담당합니다. 데이터가 평문인지 암호문인지는 전혀 알지 못합니다.

### 10.1. 에셋 업로드 (`POST /api/assets/upload`)

클라이언트(Sync 엔진)가 새로운 로컬 에셋을 클라우드에 올릴 때 호출합니다. (Multipart Form-Data 형식으로 `file` 포함)

- **요청 (Payload)**
  - `hash` (string): 에셋의 고유 해시 (파일명 역할)
  - `file` (binary blob): 물리적 바이트 배열 (이미 클라이언트에서 암호화됨)

- **서버 처리 로직 (Transaction)**
  1. `file` 용량이 하드 리미트(예: 5MB)를 초과하는지 검사. (초과 시 `413 Payload Too Large` 반환 후 거부)
  2. 에셋 관리 장부(DB)에서 `hash`의 존재 여부 조회.
  3. **[경우 A] 해시가 없음 (최초 업로드)**:
     - 유저의 남은 프라이빗 쿼타를 확인. (부족 시 `402 Payment Required` 반환 후 거부)
     - 파일을 R2(클라우드) 디렉토리에 저장.
     - 장부 테이블에 새 레코드 생성: `ownerId = 현재 유저`, `refCount = 1`, `size = 파일 용량`
     - 유저 쿼타를 `size`만큼 차감.
     - 응답: `201 Created`
  4. **[경우 B] 해시가 있음 (중복 / 무임승차)**:
     - 이미 R2에 파일이 있으므로 물리적 업로드는 스킵.
     - 해당 해시 레코드의 `kind`가 `public`인가?
       - **Public인 경우**: 이미 공개된 에셋, 그냥 스킵 (`200 OK`).
     - `kind`가 `private`인 경우, `ownerId`가 요청한 유저(본인)인가?
       - **본인(Owner)인 경우**: 자기가 두 번 임포트/업로드 한 것이므로 `refCount`만 1 증가시킴. (별도 쿼타 차감 없음)
       - **타인(Freerider)인 경우**: 그냥 스킵. (장부 업데이트도, 쿼타 차감도 없음)
     - 응답: `200 OK`

### 10.2. 에셋 삭제 (`DELETE /api/assets/:hash`)

주인(Owner)이거나 주인이 아니거나, 유저가 로컬에서 에셋을 지울 때 반드시 찔러줍니다.

- **요청 (Payload)**
  - 경로 파라미터: `:hash` (지우고자 하는 파일의 해시)

- **서버 처리 로직 (Transaction)**
  1. 장부 (DB)에서 `:hash` 레코드 조회. 없으면 이미 지워진 것이므로 무시(`200 OK`).
  2. 해당 레코드의 `kind`가 `public`인가?
     - **Public인 경우**: 퍼블릭 에셋은 삭제 불가 (`403 Forbidden`).
  3. `kind`가 `private`인 경우, `ownerId`가 요청한 유저(본인)인가?
     - **타인(Freerider)인 경우**: 본인 소유가 아니므로, 삭제할 권한도 자격도 없음. 서버는 조용히 무시 (`200 OK`).
     - **본인(Owner)인 경우**:
       - 우선 `refCount`를 1 감소시킴.
       - 만약 뺀 뒤의 `refCount > 0` 이면: (이 유저가 본인의 다른 봇에서 이 에셋을 쓰고 있다는 뜻)
         - 쿼타 환급이나 파일 삭제 없이 트랜잭션 종료 (`200 OK`).
       - **만약 `refCount === 0` 이면**: (이 에셋을 진짜 완벽히 다 지웠음!)
         - 유저의 쿼타 계좌에 `size`만큼 용량을 환급(복원)해 줌.
         - R2(클라우드) API를 호출하여 해당 스토리지를 영구 삭제.
         - 장부에서 해시 레코드 삭제.
         - (이 시점부터 프리라이더들은 404 엑박을 맞게 됨)
     - 응답: `200 OK`

### 10.3. 에셋 프로모션 (`PUT /api/assets/:hash/promote`)

프라이빗 에셋을 퍼블릭으로 변환합니다. 암호화된 파일을 평문으로 갈아끼워 Hub 공유를 가능하게 합니다.

- **요청 (Payload)**
  - 경로 파라미터: `:hash` (에셋의 해시, `assets.hash`)
  - `file` (binary blob): 평문 이미지 (복호화된 원본)

- **서버 처리 로직 (Transaction)**
  1. 요청 유저가 해당 에셋의 소유자(`ownerId`)인지 확인. (아니면 `403 Forbidden`)
  2. 해당 레코드의 `kind`가 이미 `public`인지 확인. (이미면 `200 OK` 멱등)
  3. `file`이 유효한 이미지인지 검증 (Sharp 등으로 파싱). (유효하지 않으면 `400 Bad Request`)
  4. R2에서 해당 hash 경로의 파일을 평문으로 덮어쓰기.
  5. 장부 테이블에서 레코드의 `kind`를 `public`으로 변경.
  6. 유저의 쿼타에서 `size`만큼 환급.
  7. 응답: `200 OK`

> **보안 노트**: 퍼블릭 에셋은 쿼타를 소비하지 않으므로, 스팸 방지를 위해 별도의 속도 제한(Rate Limit)이나 Hub 승인 프로세스가 필요할 수 있습니다.
> 특히, **"로그인 상태 = 무제한 퍼블릭 업로드"**가 되지 않도록 **가드레일**이 필수적입니다.

## 11. 보안 및 남용 방지 (Security & Abuse Prevention)

E2EE 환경에서 서버는 데이터의 내용을 알 수 없으므로, 악의적인 유저가 서버를 무제한 이미지 저장소로 악용하는 것을 막기 위해 **상황 기반 권한 부여(Action-based Granding)** 전략을 사용합니다.

### 11.1. 허가 기반 업로드 (Grant-based Upload)

- **프라이빗 에셋**: 유저 자신의 쿼타(Quota) 한도 내에서 자유롭게 업로드할 수 있습니다. (E2EE 상태)
- **퍼블릭 에셋/프로모션**: 단순히 로그인만 했다고 해서 퍼블릭 공간에 무제한으로 결과물을 올릴 수 없습니다. 서버는 오직 **"정당한 사유(Context)"**가 있을 때만 업로드 게이트를 엽니다.

### 11.2. 공유 트랜잭션과 임시 통행증

1.  **공유 의사 표시**: 유저가 특정 캐릭터나 모듈을 Hub에 공유하려고 할 때, 서버에 공유 의사를 먼저 전달합니다.
2.  **임시 권한 부여 (Action Token/Presigned URL)**:
    - 서버는 유저의 계정 상태와 공유하려는 컨텐츠를 검토한 후, 해당 공유에 포함된 에셋 해시(`hash`)들에 대해서만 **짧은 시간(예: 5분) 동안 유효한 업로드 허가권**을 발급합니다.
    - 이때 발급되는 허가권은 특정 해시값에만 묶여 있어, 유저가 다른 엉뚱한 파일을 퍼블릭으로 올리는 것을 원천 차단합니다.
3.  **최소 권한의 원칙**: 발급된 토큰은 해당 공유 작업이 완료되거나 만료되면 즉시 파기됩니다.

이 방식을 통해 서버는 "전체 유저에게 무제한 쓰기 권한"을 주는 대신, **"특정 시점에, 특정 에셋에 대해서만 쓰기를 허용"**하는 통제권을 유지하며 스토리지 남용과 스팸을 방어합니다.
